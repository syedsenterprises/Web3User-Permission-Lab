# Initial architecture decisions

1. Local-first: no backend, database, wallet connection, or chain deployment in milestone one.
2. Deterministic core: no AI calls or network requests inside the evaluator.
3. Fail closed: missing/malformed required inputs return UNKNOWN; explicit policy violations return DENY.
4. Simulator is not enforcement: an off-chain result cannot stop a transaction.
5. No personal data onchain; if a registry is justified later, begin with minimal hashes and lifecycle events.
6. No token in MVP.
7. Bound authorization artifacts: use versioned, deterministic length-prefixed canonical encoding and SHA-256 binding digests with an additive SQLite issued -> consumed state transition to protect against parameter tampering and replay without requiring in-memory state.
8. Ed25519 issuer authenticity: Signed authorization artifacts (version 2) cryptographically bind artifact version, authorization ID, issuer key ID, and binding digest using Ed25519 digital signatures (`node:crypto`) and length-prefixed canonical encoding. Verification strictly occurs before SQLite state transitions, ensuring forged or tampered artifacts fail closed without modifying storage.
9. Artifact version discriminator in persistent store: SQLite authorization store enforces an explicit `artifact_version` column (`NOT NULL DEFAULT 1`). V1 consumption matches `artifact_version = 1`, and signed V2 consumption matches `artifact_version = 2` inside the atomic `UPDATE` query. This guarantees cross-version isolation, ensuring unsigned V1 artifacts cannot consume V2-issued authorizations.
10. V3 Length-prefixed canonical serialization and Ed25519 artifact signatures: Signed authorization artifacts (version 3) bind artifact version (`3`), authorization ID, issuer key ID, issued-at timestamp, explicit expiry timestamp (`expiresAtSeconds`), policy ID, policy revision, and SHA-256 transaction binding digest. Encoding uses deterministic length-prefixed formatting (`web3user-signed-authorization-v3\n` with `name:length:value\n` entries) and Ed25519 asymmetric signatures (`node:crypto`). Signature verification occurs strictly before database state transitions, and the SQLite authorization store checks `artifact_version = 3` during atomic consumption. This establishes full cryptographic issuer authenticity and eliminates delimiter injection.
11. Transaction-enclosed persistent monotonic clock with rollback detection: To prevent clock manipulation and time-skew replay attacks across process restarts and multiple store instances, monotonic clock state is persisted in table `system_clock_state`. Within atomic write transactions (`BEGIN IMMEDIATE;`), the current trusted timestamp is verified against the recorded high-water mark (`trustedNowSeconds >= highWaterSeconds`). If time has regressed, the transaction fails closed, preventing backward clock jumps from validating expired or invalid authorizations.
12. Bounded SQLite contention retries with non-spinning exponential backoff: Concurrent SQLite write transactions (`BEGIN IMMEDIATE;`) under WAL mode can encounter transient `SQLITE_BUSY` errors. Instead of failing immediately or busy-waiting in a CPU-burning loop, operations use a bounded retry budget (5 attempts, 250ms cumulative budget) with randomized exponential backoff (base 15ms, max 100ms, full jitter). Delays are executed synchronously via `Atomics.wait` on a `SharedArrayBuffer` (`sleepSync`), yielding the operating system thread without spinning. If contention persists after exhausting the budget, the operation fails closed with a clear error.
13. Subtraction-first non-overflowing safe-integer TTL expiry calculation: In JavaScript, adding an untrusted or maximum TTL (`Number.MAX_SAFE_INTEGER`) to `effectiveNowSeconds` causes integer overflow beyond 2^53 - 1, resulting in precision loss and broken timestamp comparisons. Expiration calculations must calculate the remaining safe duration first: `remainingValidSeconds = maxAllowedExpiresAt - effectiveNowSeconds`, where `maxAllowedExpiresAt` is bounded by policy expiry, key expiry, and `Number.MAX_SAFE_INTEGER`. If `ttlSeconds >= remainingValidSeconds`, the expiration clamps safely to `maxAllowedExpiresAt`; otherwise, addition is performed safely. The result is verified to be a positive safe integer strictly greater than `effectiveNowSeconds`.
14. Multi-process concurrency barriers and process-crash rollback invariants: Concurrency and crash durability are verified through explicit multi-process testing. A 4-process IPC rendezvous barrier releases competing OS processes simultaneously to consume the exact same V3 authorization, strictly verifying that exactly one worker succeeds (`ALLOW`) while three fail closed (`DENY`), and proving that SQLite's lock guarantees prevent double-consumption under high write contention. Process-crash tests verify that abrupt worker termination (`SIGKILL` or `process.exit(1)`) mid-transaction triggers automatic WAL recovery upon database reopen, ensuring uncommitted writes and clock updates are rolled back cleanly without leaving orphaned records. These tests verify process-crash recovery; physical power-loss durability remains bounded by host filesystem and hardware write caches.
15. Milestone 6.5 security hardening across contention backoff, fail-closed defaults, atomic key lifecycle, and input bounds: SQLite contention retries enforce non-spinning exponential backoff with full jitter (5 attempts, 15ms base, 100ms max, 250ms cumulative budget) using `sleepSync` via `Atomics.wait`. `SQLiteAuthorizationStore` defaults to fail-closed strict mode (`allowLegacyArtifactVersions: false`), requiring explicit opt-in for legacy V1/V2 operations. Key lifecycle mutations (`registerKey`, `retireKey`, `revokeKey`) execute clock high-water mark validation and advancement atomically within the same write transaction as key table mutations, ensuring failed operations roll back clock updates cleanly. Authorization IDs are bounded to a maximum length of 128 characters across lifecycle, cryptographic, and storage layers; transaction envelopes enforce an early calldata sanity bound of 131,074 characters (64 KB).
16. Milestone 6.7 individual authorization cancellation and bounded process-local memory: `SQLiteAuthorizationStore` and `authorization-lifecycle.ts` implement atomic individual cancellation (`cancelAuthorization` / `cancelSignedTransactionAuthorizationV3`). The transition from `issued` to `cancelled` occurs atomically in SQLite under write transactions (`BEGIN IMMEDIATE;`). Cancelled authorizations fail closed on subsequent consumption attempts and cannot be re-issued due to primary-key constraints. Concurrency races between cancel and consume strictly resolve with exactly one winning operation and the losing operation failing closed. Process-local in-memory state enforces a strict fail-closed ceiling (`MAX_PROCESS_LOCAL_CONSUMED_IDS = 10_000`) without LRU eviction to prevent replay vulnerabilities; persistent store callers do not populate process-local memory, and envelope tracking uses `WeakSet<object>` with automatic garbage collection.
17. Milestone 6.8 Phase 1 clock guardrails and two-phase candidate transaction integrity: `ClockGuard` pairs wall-clock time with process monotonic nanoseconds (`process.hrtime.bigint()`). Inside serialized SQLite write transactions (`BEGIN IMMEDIATE;`), candidate samples are validated against persistent high-water and symmetric divergence bounds (step velocity: +10s forward, -5s backward; cumulative divergence ceiling: 60s; anchor lifetime: 24h; startup forward gap: 3600s). In multi-process deployments, a worker's local published sample may lag behind the authoritative SQLite high-water mark; candidate timestamps below shared high-water are rejected without falsely tripping the process anchor. Local candidate samples are published in memory strictly upon confirmed successful `COMMIT;`. If business evaluation or SQLite mutations fail, the transaction rolls back and the candidate is discarded. If `COMMIT;` throws or its outcome is uncertain, the database connection is marked tainted and closed, the clock guard permanently trips to `TRIPPED_CLOSED`, and all subsequent authorization decisions fail closed. An anti-time-travel check (`artifact.issuedAtSeconds <= candidate.wallSeconds`) prevents future-dated artifact consumption.
18. Milestone 6.11 explicit SQLite durability policy and storage failure boundaries: Every file-backed SQLite database connection opened by `SQLiteAuthorizationStore`, `SQLitePolicyStore`, and `SQLiteKeyStore` explicitly enforces `PRAGMA journal_mode = WAL;` and `PRAGMA synchronous = FULL;` (with optional configurable override). Because SQLite's `synchronous` pragma is connection-scoped rather than stored in the database header, each independently opened store connection configures its pragma upon initialization, while borrowed connections inherit the parent configuration. In WAL mode, `synchronous = FULL` ensures an operating-system-level disk sync (`FlushFileBuffers` / `fsync`) executes upon every transaction `COMMIT;`, protecting committed authorization consumption and governance updates against abrupt OS crashes and power failures that honor cache flushes. Durability guarantees are bounded across three tiers: (a) Process-crash recovery is guaranteed by WAL atomic rollback; (b) OS-crash durability is guaranteed by `FULL` sync on commit; (c) Physical power-loss durability remains bounded by host drive firmware and write caching (e.g. consumer SSDs lacking power-loss protection that buffer writes in volatile DRAM).
